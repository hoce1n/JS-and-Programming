# Reachability و Garbage Collector

## Problem

در Heap نمی‌توان فقط گفت «آخرین چیزی را که ساخته‌ایم حذف کن». ممکن است Object قدیمی هنوز لازم باشد،
درحالی‌که Object جدیدتری دیگر کاربردی نداشته باشد. بنابراین ترتیب ساخت، معیار قابل‌اعتمادی برای
آزادسازی نیست.

## Computational Need

Runtime باید بتواند تشخیص دهد کدام Objectها هنوز از مسیرهای معتبر قابل دسترسی‌اند و کدام Objectها
دیگر هیچ استفاده‌ای ندارند. سپس باید فضای Objectهای غیرقابل‌دسترسی را دوباره قابل‌استفاده کند.

## Concept

**Reachability** یعنی قابل‌دسترسی بودن یک Object از مسیرهای ریشه‌ای و Referenceهای فعال برنامه.
به‌صورت مفهومی:

```text
Still reachable?
      ↓
YES → keep
NO  → reclaim
```

این نیاز به **Garbage Collector** را ایجاد می‌کند؛ سامانه‌ای که Objectهای غیرقابل‌دسترسی را شناسایی
و Reclaim می‌کند.

مسیر کامل‌تر:

```text
Need to preserve results
        ↓
Need State
        ↓
State needs Memory
        ↓
Memory needs Lifetime
        ↓
Lifetimeها یکسان نیستند
        ↓
Stack (ترتیب عمر مشخص است)
Heap  (ترتیب عمر مشخص نیست → Reachability + GC)
```

## Language Feature

در JavaScript، Runtime به‌صورت خودکار مدیریت Garbage Collection را انجام می‌دهد. برنامه‌نویس معمولاً
مستقیماً Object را آزاد نمی‌کند؛ بلکه با حذف Referenceهای غیرضروری، امکان غیرقابل‌دسترسی شدن آن را
فراهم می‌کند.

## Syntax

```js
let user = { name: "Ali" };

console.log(user.name); // Object قابل دسترسی است.

user = null;
// اگر Reference دیگری به Object وجود نداشته باشد، اکنون برای Reclaim شدن واجد شرایط است.
```

واجد شرایط بودن برای Reclaim شدن به معنی آزادسازی فوری و قابل‌مشاهده توسط برنامه نیست؛ زمان‌بندی
داخلی به Runtime واگذار می‌شود.

## Personal Notes & REPL Verification

ملاک اصلی Garbage Collector «قدیمی‌تر بودن» نیست، بلکه Reachability است. همچنین باید بین «دیگر از
مسیر برنامه قابل دسترسی نیست» و «همین لحظه حافظه‌اش آزاد شده» تفاوت بگذارم.
